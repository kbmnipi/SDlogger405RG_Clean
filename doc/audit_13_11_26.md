## 2. BUG-1 - КРИТИЧЕСКИЙ: физический конфликт PA5 (SPI1_SCK и DAC_OUT)

Факт. src/spi.c HAL_SPI_MspInit():
GPIO_InitStruct.Pin = GPIO_PIN_5 | GPIO_PIN_6 | GPIO_PIN_7;
GPIO_InitStruct.Alternate = GPIO_AF5_SPI1; HAL_GPIO_Init(GPIOA, &GPIO_InitStruct);

Факт. src/main.c:120: MX_ADC1_Init() -> src/adc.c HAL_ADC_MspInit():
GPIO_InitStruct.Pin = GPIO_PIN_0 | GPIO_PIN_1 | GPIO_PIN_2; (аналог).

Факт. docs/WEACT_F405_PINOUT.md раздел 6: SPI1_SCK - PA5; раздел 5 "HIL vs
Production Pin Conflict (flagged...)": "Production (LIS3DSH): PA5 = SPI1_SCK".

Механика отказа. Инициализация в main() идет в порядке: MX_SPI1_Init()
(строка 105) -> MX_ADC1_Init() (строка 120). Оба вызывают HAL_GPIO_Init(GPIOA, ...).
CubeMX-конфигурация ADC-пинов не трогает PA5 (он только в SPI-маске), поэтому PA5
остается AF5 (SPI1_SCK). PA5 физически не может одновременно быть SPI1_SCK
(AF_PP, AF5) и DAC_OUT1 (аналог). В HIL-схеме DAC->ADC loopback (PA5 -> PA0/1/2)
это единственная точка впрыска сигнала.

Последствия (все три сценария плохие):

1. С LIS3DSH подключенным (PA5 = SCK): такты SPI идут на вход DAC-сети,
   "сигнал" ADC = шум SPI, тест бессмысленен.
2. С PA5 переназначенным под DAC: SPI1 не имеет SCK -> HAL_SPI_TransmitReceive
   зависает на SPI_FLAG_TXE/RXNE до HAL_TIMEOUT (см. BUG-6) -> lis3dsh_err=1 ->
   смерть на 1-м такте.
3. MX_ADC1_Init() теоретически может конфликтовать с GPIO_MODE_AF_PP на PA5
   при пересоздании.

Решение (обязательный выбор, pinout-совместимое):

| Вариант | Пины | Комментарий |
| --- | --- | --- |
| A (рекомендуется) - SPI2 для LIS3DSH | SCK PB10, MISO PB14, MOSI PB15, CS PA4 (или PB12) | Все 4 входа в docs/WEACT_F405_PINOUT.md раздел 6, таблица "SPI2 (Alternative)". AF5_SPI2. PA5 остается DAC. SPI2 на APB1 (42 MHz), при prescaler 16 = 2.625 MHz - даже быстрее текущего SPI1 (1.3125 MHz). Требуется добавить hspi2 в CubeMX, новых пинов из воздуха не берем: PB10/PB14/PB15 явно перечислены в pinout. |
| B - DAC2 на PA6 | DAC_OUT2 = PA6 (STM32F405), PA6 уходит из SPI1_MISO | flag: PB14 = SPI2_MISO в pinout остается, но перенос SPI1_MISO на PA4 ломает зафиксированный CS. Не рекомендую. |
| C - DAC->ADC через внешнюю перемычку на PB0/PB1 | PB0/PB1 в pinout: "User GPIO (Header P2)" | pinout не дает им роль ADC. TBD in pinout (ADC1_IN8=PB0 / IN9=PB1 в docs/WEACT_F405_PINOUT.md не перечислены), требуется подтверждение, сам не назначаю. |

Дополнительно (не баг, но конфликт CubeMX-проекта): HIL-файлы dac.c / adc.c,
которые вы скидывали ранее, сейчас физически отсутствуют в src/ (src/ = main.c,
sd_writer.c, lis3dsh.c, tim.c, adc.c, spi.c, sdio.c, ... - dac.c нет), но main.c
уже содержит #include "adc.h", MX_ADC1_Init(), ADC_SAMPLETIME_84CYCLES.
Проект в смешанном состоянии: adc.c/.h сгенерированы (значит в .ioc ADC1 включен),
dac.c/.h - location TBD. Перед сборкой HIL-3 обязательна полная перегенерация .ioc.

## 3. BUG-2 - КРИТИЧЕСКИЙ: приоритет TIM2_IRQHandler = 0 (равен SysTick)

Факт. src/tim.c HAL_TIM_Base_MspInit(): HAL_NVIC_SetPriority(TIM2_IRQn, 1, 0);
Факт. include/main.h: #define VIBL_ISR_PRIORITY 0u;
src/main.c (~125): HAL_NVIC_SetPriority(TIM2_IRQn, VIBL_ISR_PRIORITY, 0u);
-> итоговый приоритет 0.
Факт. include/stm32f4xx_hal_conf.h:151: #define TICK_INT_PRIORITY 0U
-> TICK_INT_PRIORITY = 0.
Проверка HAL_Init() (stm32f4xx_hal.c):
if (HAL_SYSTICK_Config(SystemCoreClock / (1000U / uwTickFreq)) > 0U) error;
-> при SysTick = 0 срабатывает ветка Error_Handler(), HAL_Init() вернет HAL_ERROR.

Механика. На Cortex-M4 приоритет 0 = наивысший. SysTick (обновление uwTick,
stm32f4xx_hal.c:94 __IO uint32_t uwTick;, :314 uwTick += uwTickFreq;) имеет
приоритет 0. Если SysTick уже выполняется или находится в pending, TIM2-ISR
(0, sub 0) его не preempt-ит. Любой код в TIM2-ISR с HAL_GetTick()-timeout
(см. BUG-6) ждет тик SysTick. Классический deadlock-паттерн HAL_*_Timeout
при приоритете 0.

Дополнительно: в проекте три обработчика уровня 0 (TIM2) против SDIO_IRQn = 2
(src/sdio.c:106) и RTC_WKUP_IRQn = 3 (src/rtc.c:132).

Фикс (минимальный диф):

```c
/* USER CODE BEGIN TIM2_Init 2 */
HAL_NVIC_SetPriority(TIM2_IRQn, 5, 0);  /* ниже SysTick(0) и SDIO(2); критичный путь все равно жесткий */
/* USER CODE END TIM2_Init 2 */
```

и в main.c удалить повторное HAL_NVIC_SetPriority(TIM2_IRQn, ...) (оно
переопределяет MspInit и является источником ошибки).
VIBL_ISR_PRIORITY 0u заменить на 5u.

Обоснование числами: jitter тактов 1600 Hz = 625 мкс; задержка SysTick-обработчика
~1-2 мкс. Даже приоритет 5 дает worst-case задержку входа в TIM2 менее 3 мкс
(0.5% периода) - допустимо. Приоритет 0 дает неограниченную задержку при
SysTick-collision.

(Полярность корректна по pinout: "SD_Card_Detect (CD) PA8 ... Замыкается на GND,

## 6. BUG-5 - Гонка ping-pong: ISR пишет в ту же половину буфера, которую main отдает в FatFs

Факт. src/main.c:54: static int16_t pingpong_buf[VIBL_SAMPLES_PER_CHUNK * 2u * 3u];
(1200 samples x 3 = 3600 int16 = 7200 B), :55 sample_idx, :56 buf_ready.
Факт. ISR (:203-220): пишет в pingpong_buf[sample_idx++];
sample_idx == 1800 -> buf_ready = 1 (НЕ сбрасывает sample_idx);
sample_idx == 3600 -> sample_idx = 0, buf_ready = 2.
Факт. main (:138-147): читает buf_ready == 1 ->
vibl_write_chunk(&pingpong_buf[0], 600); buf_ready == 2 ->
vibl_write_chunk(&pingpong_buf[1800], 600).

Механика отказа. Когда buf_ready == 1, ISR продолжает писать samples 600..1199
в тот же массив с индекса 1800 (вторая половина) - это ок. Но когда
buf_ready == 2 (после 1200 samples), ISR обнуляет sample_idx и начинает писать
в &pingpong_buf[0], в то время как main еще может находиться внутри
vibl_write_chunk(&pingpong_buf[0], ...) (половина "ping" еще не записана на SD).
Т.е. половина "ping" пишется на SD одновременно с тем, как ISR перезаписывает ее
новыми сэмплами. Результат - недетерминированное смешение двух временных окон
в одном чанке: данные на SD перестают быть непрерывной последовательностью
во времени, при этом CRC в файле будет внутренне корректной (CRC считается
по уже испорченному буферу). Худший из возможных отказов: файл "валиден",
но физически бессмысленен.

Дополнительная гонка. buf_ready - volatile uint8_t, но read-then-clear в main
(buf_ready = 0 до записи) и запись в ISR не атомарны относительно друг друга
по смыслу (ISR может выставить buf_ready = 1 сразу после buf_ready = 0 ->
чанк 600 сэмплов теряется без gap_counter).

Фикс (проверенная ранее SPSC-модель из docs/reference_vibro_architecture.md,
концепция, не код):

```c
/* USER CODE BEGIN PV */
#define VIBL_CHUNK_SAMPLES 600u
#define VIBL_CHUNK_WORDS   (VIBL_CHUNK_SAMPLES * 3u)   /* 1800 */
static int16_t arena[2][VIBL_CHUNK_WORDS];
static volatile uint8_t  fill_idx  = 0u;   /* writes 0/1 only */
static volatile uint32_t fill_cnt  = 0u;   /* < VIBL_CHUNK_WORDS */
static volatile uint8_t  full_mask = 0u;   /* bit0 = arena[0] full, bit1 = arena[1] full */
/* USER CODE END PV */

void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim)
{
    if (htim->Instance != TIM2) return;
    if (++g_tick != next_due_tick) { pending++; return; }   /* см. BUG-7 */
    next_due_tick += g_period_ticks;
    int16_t *b = arena[fill_idx];
    if (lis3dsh_read(&b[fill_cnt], &b[fill_cnt + 1], &b[fill_cnt + 2]) != 0) {
        lis_err = 1u;
        return;
    }
    fill_cnt += 3u;
    if (fill_cnt >= VIBL_CHUNK_WORDS) {
        full_mask |= (uint8_t)(1u << fill_idx);
        fill_idx ^= 1u;
        fill_cnt = 0u;
    }
}
```

main: if (full_mask & 1u) { full_mask &= ~1u; vibl_write_chunk(arena[0], VIBL_CHUNK_SAMPLES); }
- арена 0 гарантированно больше не пишется ISR (ISR уже перешел на fill_idx = 1).
Требование: запись чанка не более 375 мс, иначе потеряется следующий чанк
(см. VERDICT-1 по бюджету).

## 7. BUG-6 - HAL_Delay() внутри hil1_error_loop() при приоритете 0 + SPI-timeout в ISR

Факт. src/main.c:226-234: цикл мигания LED с HAL_Delay(200) и HAL_IWDG_Refresh()

Факт. stm32f4xx_hal.c:390 __weak void HAL_Delay(uint32_t Delay) - spin на
HAL_GetTick(), зависящий от SysTick (приоритет 0, TICK_INT_PRIORITY 0U).
Факт. src/lis3dsh.c:36 HAL_SPI_TransmitReceive(..., LIS3DSH_SPI_TIMEOUT_MS /*10*/);

- (б) hil1_error_loop() не должен вызываться из ISR (сейчас корректно - из main);
- (в) LED-мигать через счетчик цикла, а не HAL_Delay (если вызывается из

## 8. BUG-7 - Пропущенные такты не считаются, потеря метки времени (нарушение требования непрерывности)

Факт. ISR делает ровно один lis3dsh_read() на каждое срабатывание TIM2 UI.
TIM2 = свободный runs @1600 Hz (AutoReloadPreload = DISABLE, src/tim.c).
Если ISR задержан (preemption, SDIO-транзакция на приоритете 2 не мешает, но
SysTick/DMA/иной ISR мешает), UI-флаг TIM2 сбрасывается в HAL до входа в callback:
stm32f4xx_hal_tim.c:3954-3958:

```c
if ((itsource & (TIM_IT_UPDATE)) == (TIM_IT_UPDATE)) {
    __HAL_TIM_CLEAR_FLAG(htim, TIM_FLAG_UPDATE);
    htim->PeriodElapsedCallback(htim);
}
```

-> пропущенные UI не аккумулируются (TIM_SR_UIF - один бит,
stm32f405xx.h:11741 TIM_SR_UIF_Pos (0U)).

Последствие. 384000 чанков за 4 ч; если суммарно потеряно N срабатываний, файл
содержит 384000 x 600 - N записей, но никакого маркера, где именно произошел
пропуск (скачок seq по чанкам фиксируется только если потеряно 600 сэмплов
подряд -> потеря менее 600 сэмплов невидима вообще). Требование HIL-3
"непрерывность 1600 Hz" без gap_counter не выполняется.

Фикс (детерминированный учет, без DWT): опорный счетчик тиков TIM2 + пропущенные
тики -> vibl_mark_gap():

## 11. Проверенные "хорошие" находки (подтверждено корректным)

1. CTRL_REG4 = 0xAF: 0xA0 = 1600 Hz по присланному ST lis3dsh.h; BDU=1 (бит3=1);
   EN_XYZ=111.
2. CTRL_REG5 = 0x20: bit 5..3 = 100 -> FSCALE = +/-16 g; bit2..1 = 00 ->
   BW = 800 Hz; bit0 SIM=0 -> 4-wire.
3. CTRL_REG6 = 0x00: IF_ADD_INC=0 -> автоинкремент отключен; автоинкремент
   в транзакции задается битом 0x40 в адресе (SPI_AUTO_INC_BIT).
4. Смещение WHO_AM_I = rx[1]: HAL polling-цикл (stm32f4xx_hal_spi.c:1286-1329)
   читает RXNE после записи DR (txallowed-логика), поэтому rx[0] - MISO во время
   1-го байта (неопределен), rx[1] - ответ на адрес 0x8F.
5. Порядок OUT_X_L -> OUT_X_H (rx[1]=L, rx[2]=H): LIS3DSH little-endian,
   адрес 0x28 = X_L, 0x29 = X_H; инкремент адреса. *x = (rx[2] << 8) | rx[1].
6. TIM2 = 119/399: (119+1) x (399+1) = 48 000; 168 MHz/48 000 = 1600.000 Hz
   (при условии 168 MHz - см. BUG-10).
7. Полярность CD (PA8): (GPIOA->IDR & PIN_8) != 0 -> absent, соответствует
   pinout п.2.
8. CRC хедера в C: temp_crc = hdr_crc; hdr_crc = 0; на offset 52 (DWORD-aligned),
   затем memcpy(..., 252) - совпадает с полем 0..251 (расхождение - в парсере,
   WARN-10).
9. _FS_TINY 0, _FS_REENTRANT 0, _FS_LOCK 0, _VOLUMES 1, _USE_LFN 0 - согласовано
   с 8.3-именем и single-thread main loop.
10. f_open(FA_CREATE_ALWAYS, FA_WRITE) - в исходнике обоснование отсутствует.
11. IWDG-refresh в disk_read / disk_write защищает длинные SD-транзакции
    (но не спасает при 5 с CMD-таймаутах - WARN-12).
12. EXTI на PC13 уже настроен (gpio.c: GPIO_MODE_IT_RISING) - готовый механизм
    graceful-stop для vibl_close(), free win.

## 12. VERDICT-1 - Бюджет времени чанка (главный проектный риск)

Данные: 1600 samples/s x 6 B = 9 600 B/s payload; чанк 600 samples = 4 100 B;
интервал 375 ms.

SDIO 1-bit @ ClockDiv = 16 (src/sdio.c:47), SDIO_CK = SDIOCLK/(2*16+2) =
42 MHz/34 = 1.2353 MHz (APB1 = 42 MHz при 168 MHz SYSCLK, APB1 prescaler 4)
-> полезная скорость 1-бит = 1.235 MByte/s -> 4 100 B данных = 3.32 ms.

Но FatFs добавляет (на каждый чанк):

- 1x create_chain -> чтение FAT-сектора + запись FAT-сектора (write-back через
  sync_window, ff.c:883) = 2 x 512 B = 1.0 ms + 2 x HAL_Delay(10) = 20 ms
- 1x directory-обновление при росте файла (каждый новый кластер, т.е. каждые
  csize*512/41000 чанков; для csize = 8 -> каждые ~1 чанк) = 1 x 512 B +
  HAL_Delay(10) = 11 ms
- RMW частичного сектора (WARN-11) ~ +0.5..1 sector-read + write = 1 ms + 10 ms delay

Итого worst case на чанк ~ 46 ms (из них ~40 ms - HAL_Delay(10) в disk_write),
т.е. 12% duty cycle. Формально 375 ms хватает -> пропускная способность
достаточна даже в 1-bit режиме.

НО если убрать HAL_Delay(10) и включить 4-bit
(HAL_SD_ConfigWideBusOperation(SDIO_BUS_WIDE_4B) при проверенной стабильности):
4-bit @1.2353 MHz = 4.94 MB/s -> чанк = 0.83 ms + FAT-оверхед ~2 ms = 3 ms,
duty = 0.8% -> остается 372 ms запаса на 4 аренных буфера (16 чанков = 6 с
буферизации) вместо 2 чанков (750 ms) сейчас.

Рекомендация (стратегическая, без кода):

1. Оставить 1-bit как аттестованный режим HIL-3 (стабильность уже проверена
   в HIL-1 - "4-bit experiment failed, reverted to 1-bit" по комментарию
   diskio.c), но удалить HAL_Delay(10) -> duty 12% -> 3%.
2. Добавить третью арену (арена 3 x 7200 B = 21.6 KB - бюджет SRAM позволяет) ->
   буфер 1.125 s вместо 750 ms. Это превращает "пропуск чанка при 46 мс glitch"
   в "пропуск при 1.1 s glitch".
3. Аттестовать 4-bit отдельным мини-тестом (4 ч, 8-секторные кластеры,
   ClockDiv = 4 -> SDIO_CK = 42 MHz/(2*4+2) = 7.0 MHz, но с VERY_HIGH GPIO
   и без DMA риск again; безопаснее ClockDiv = 8 -> 4.21 MHz) и только потом
   применять для production-логгера.

VERDICT-1: 1600 Hz на 1-bit SDIO реализуема (duty 3..12%), узкое место - не SDIO,
а HAL_Delay(10) + поштучные FatFs write-back-записи. Бюджет SRAM избыточен:
доступны 192 KB D1 + 64 KB CCM при текущем использовании ~8.5 KB.

VERDICT-2 (алиасинг / BW): BW = 800 Hz при ODR 1600 Hz означает, что анти-алиасинг
полоса = Nyquist-граница. Для HIL-теста DAC(PA5) -> ADC(PA0/1/2) с искусственным
сигналом: если тестовый сигнал содержит гармоники выше 800 Hz, они заалиасятся
в полосу и будут неотличимы от реальных данных. Рекомендую в HIL-3 ограничить
тестовый сигнал до 400 Hz и в отчете указать bandwidth_hz = 50 (при BW = 50 Hz)
ИЛИ оставить BW = 800 и документировать отсутствие защиты.
docs/LIS3DSH_Датчик_описание.md: "при 1600 Hz фильтр отключен" - UNCERTAIN,
требует подтверждения по DS; при BW = 800 Hz фильтр присутствует физически,
но его полосы недостаточно. Это форматное решение: поле bandwidth_hz в хедере
(sd_writer.h:67) должно отражать реальное значение: записать 800, а не 50.
Сейчас vibl_open(..., 16u, 100u) - параметр bandwidth вообще не передается
(vibl_open(filename, sensor_type, range_g, gain) - сигнатура sd_writer.h:114
не имеет bandwidth-аргумента), а vibl_hdr.bandwidth_hz = 0 (sd_writer.c:164)
-> BUG-11 (minor форматный): bandwidth_hz = 0 в записанном хедере.
