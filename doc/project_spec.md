# ПОЛНАЯ ТЕХНИЧЕСКАЯ ХАРАКТЕРИСТИКА ПРОЕКТА: Standalone Vibration Logger V2

## 1. Концепция и цель проекта

Проект представляет собой полностью автономный (standalone) логгер вибрации.
Устройство предназначено для непрерывного считывания данных с 3-осевого
акселерометра с частотой ровно 1600 Гц, буферизации этих данных в оперативной
памяти и последующей записи на SD-карту в собственном бинарном формате VIBL
(Vibration Log). Устройство не требует подключения к ПК во время работы и
защищено от зависаний с помощью аппаратного сторожевого таймера (IWDG).

## 2. Аппаратная платформа и периферия

- Микроконтроллер: STM32F405RGT6 (ядро Cortex-M4, 168 МГц).
- Датчик: LIS3DSH (3-осевой акселерометр, подключается по шине SPI1).
- Хранилище: MicroSD-карта, подключенная через аппаратный интерфейс SDIO (4-bit).
- Управление и индикация: синий светодиод (PB2) для индикации статуса и ошибок.

Распределение пинов (сгенерировано в CubeMX):

- PA4 - CS (Chip Select) для акселерометра (управляется программно).
- PA5, PA6, PA7 - SCK, MISO, MOSI для SPI1.
- PC8 - PC12, PD2 - шина SDIO.
- PB2 - светодиод состояния (Active HIGH).

## 3. Архитектура сбора и обработки данных (Data Flow)

Система построена по принципу Producer-Consumer (Производитель-Потребитель)
с разделением времени.

### 3.1. Производитель (прерывание TIM2)

Таймер TIM2 настроен на частоту ровно 1600 Гц (период 625 мкс). Каждые 625 мкс
генерируется прерывание:

1. Внутри функции HAL_TIM_PeriodElapsedCallback вызывается драйвер lis3dsh_read().
2. Драйвер осуществляет блокирующее чтение по SPI (7 байт: команда + 6 байт
   данных X, Y, Z). Время чтения на скорости ~1.3 МГц составляет около 48 мкс,
   что составляет менее 8% от периода. Это гарантирует, что прерывания не будут
   накладываться друг на друга.
3. Полученные данные (int16_t x, y, z) записываются в статический Ping-Pong буфер.

### 3.2. Буферизация (Ping-Pong)

Буфер представляет собой статический массив на 24 КБ (две половины по
2048 сэмплов x 3 оси x 2 байта).

- Прерывание заполняет половину A. Когда она заполняется (проходит 1.28 секунды),
  флаг buf_ready устанавливается в 1.
- Прерывание продолжает писать в половину B. Когда заполняется она - флаг
  становится 2, а индекс записи сбрасывается на начало половины A.
- Зачем это нужно: пока главный цикл медленно пишет данные на SD-карту,
  прерывание продолжает собирать данные во вторую половину буфера. Потери данных
  не происходит.

### 3.3. Потребитель (главный цикл)

Главный цикл while(1) в main.c следит за флагом buf_ready.

- Если флаг равен 1 или 2, главный цикл берет указатель на заполненную половину
  и отправляет её на запись через функцию vibl_write_chunk().
- После успешной записи флаг сбрасывается в 0.
- В каждой итерации цикла кормится сторожевой таймер HAL_IWDG_Refresh().

## 4. Кастомные реализации (что мы написали сами и зачем)

В проекте используются сгенерированные CubeMX файлы (HAL, инициализация шин),
но ключевая логика написана кастомно.

### 4.1. Драйвер датчика (lis3dsh.c / lis3dsh.h)

- Зачем: стандартные BSP-библиотеки ST слишком громоздкие и содержат лишний код.
  Наш драйвер минималистичен.
- Особенности:
  - Не настраивает SPI и GPIO (это делает CubeMX), а только управляет пином CS
    (PA4) через cs_low() и cs_high().
  - Использует Burst Read (0xE8), чтобы за одно обращение вычитать сразу
    6 регистров (X_L, X_H, Y_L, Y_H, Z_L, Z_H). Склейка осей происходит по формуле
    Little-Endian: (rx[2] << 8) | rx[1].
  - Регистры инициализации (абсолютная истина по даташиту):
    CTRL_REG4 = 0x9F (ODR 1600 Hz, BDU = 1, XYZ = 1),
    CTRL_REG5 = 0x20 (+/-16 g),
    CTRL_REG6 = 0x10.

### 4.2. Формат и запись файла (sd_writer.c / sd_writer.h)

- Зачем: обычные CSV-файлы слишком большие и медленно пишутся. Нам нужен быстрый
  и надежный бинарный формат.
- Что делает:
  - Формирует заголовок файла (Magic "VIBL", частота, количество осей).
  - Пишет данные чанками (кусками). Один чанк = заголовок чанка (с порядковым
    номером) + 2048 сэмплов данных.
  - Использует f_sync() после каждого чанка - это гарантирует, что при внезапном
    отключении питания последние успешно записанные чанки не повредятся.

### 4.3. Обработка ошибок и Watchdog (главный цикл и прерывания)

- Зачем: микроконтроллер должен работать автономно. Если возникнет ошибка шины
  или SD-карты, устройство не должно "умереть" молча.
- Что делает:
  - Функция hil3_error_loop(err_code) мигает светодиодом определенное количество
    раз (от 1 до 5) и бесконечно повторяет цикл.
  - Критически важно: внутри цикла ошибки обязательно кормится IWDG
    (HAL_IWDG_Refresh). Если этого не делать, Watchdog перезагрузит МК прямо
    во время мигания, и оператор увидит лишь "одно короткое мигание",
    зацикленное перезагрузкой, что скроет реальную причину.

## 5. Формат выходного файла (VIBL)

В результате работы на SD-карте создается файл (например, LOG0003.VIB), который
затем парсится на ПК скриптом parser_vibl.py.

- Header (заголовок): содержит метаданные (частота 1600, тип датчика).
- Chunks (чанки): идут друг за другом. В каждом чанке: Seq_Number (номер
  по порядку), Sample_Count (количество сэмплов) и сами данные.
- Trailer (трейлер): пишется только при корректном завершении записи. Содержит
  общее количество сэмплов и CRC32 всего файла для проверки целостности.

## 6. Взаимодействие файлов в проекте

- main.c - дирижер. Инициализирует периферию, запускает таймер, крутит главный
  цикл и обрабатывает прерывания.
- lis3dsh.c - "переводчик" с языка STM32 на язык датчика LIS3DSH.
- sd_writer.c - "архивариус", который берет данные из оперативной памяти
  и складывает их в бинарный файл по правилам формата VIBL.
- ff.c, diskio.c - системный слой FatFs, который общается с файловой системой
  SD-карты (скрывает от нас сложность работы с секторами).
- tim.c, spi.c, sdio.c, gpio.c - сгенерированные CubeMX файлы конфигурации
  "железа". В них мы не вмешиваемся, кроме установки правильного периода
  (ARR = 419) в tim.c.
